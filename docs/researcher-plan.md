# Researcher: published use of Statistics Canada data

**Direction agreed for planning, 2026-09-30; pilot updated 2026-10-01:** pursue published-work → survey/cycle links before IMDB questionnaire → variable links. Researcher focuses on publications issued outside Statistics Canada; its own publications are already structured separately and can be connected later by survey, cycle, and theme. A local JSONL → SQLite queue → Hermes extraction → human review pipeline lives in `tools/research/researcher`; a three-work reviewed static preview now appears in the Hub. The [pilot report](researcher-pilot-2026-10-01.md) records sources, results, and repairs. Automated source adapters, a larger gold set, durable hosted catalogue, and coverage metrics remain planned. For storage, compare Cloudflare D1 with Supabase first. Oracle is deferred because its operational setup is disproportionate to this catalogue.

## Product goal and scope

Researcher will show *documented published use* of Statistics Canada data by outside authors and organizations: which public works used a survey, which cycles they used when the work says so, and what research themes the work addresses. Statistics Canada-issued publications are excluded even if an outside index lists them. Record the issuing organization separately from the discovery source so this boundary remains reliable. The Hub and Searcher About page link to a small reviewed pilot catalogue. A later **Usage of Data** entry in Searcher will open Researcher with a survey/cycle filter. Researcher owns outside publication discovery, search, browsing, and usage metrics; Searcher continues to own variables, concepts, and derivation lineage. Extract variable names when a work supplies them so reviewed links can eventually connect to the Supabase knowledge graph. Survey-level evidence must never imply variable-level use.

The first useful path is `Searcher survey/cycle → published works → public authors and related works using the same data`. Collaboration discovery can begin with public work and author links. A claimable researcher profile or contact workflow would be a later opt-in feature; matching two authors by name alone must not merge their identities.

These are **research outputs and documented data-use counts**, not outcomes or impact measures. A paper citing CCHS establishes a literature–data link; only evidence that it analyzed CCHS supports an `analyzed` use claim. The catalogue counts *publications found and linked by this pipeline*, not every analysis, data access, researcher, or project using Statistics Canada data. A publication can use several datasets; count it once in the all-works total and once per reviewed `analyzed` dataset relationship in per-survey views. Expose source coverage and unresolved-cycle counts beside metrics.

### Minimum record and honest missingness

For **every candidate work**, attempt to extract and retain the following. A public usage record requires a reviewed `analyzed` survey claim; missing evidence remains an explicit gap, never a guessed value.

| Field | Extraction and display rule |
| --- | --- |
| Work | Canonical title, public URL/DOI or source ID, publication year/date, work type, issuing organization, and every catalogue in which it was found. Exclude Statistics Canada-issued works; deduplicate the remainder before counting. |
| Survey | One or more canonical Statistics Canada programs, with the original wording and evidence location. A background mention is recorded but does not count as use. |
| Cycle | One or more exact cycles when the work names them; otherwise preserve a stated range or `cycle not stated`. Do not derive a cycle from publication year or a bibliography coverage label. |
| Theme | One **primary** research theme and zero or more additional themes. Hermes can propose these from the abstract/full text using a versioned theme vocabulary; a reviewer checks the result and may override it. Paper-level themes are distinct from survey subject tags. If the text is insufficient, leave the primary theme unresolved for review. |
| Abstract | Capture source, language, rights status, and text where permitted. If none is available or republication is restricted, display the source link and an original short summary when supportable; do not invent an abstract. |
| Variables | Optional, verbatim variable name/code, survey/cycle context, and evidence location. A paper's named construct or questionnaire wording is not automatically a released variable. Keep unresolved mentions and reviewed `corpus_variable.record_id` links separate. |

The first academic release aims to populate survey, cycle, primary theme, and permitted abstract for each work, while accepting explicit `cycle not stated` or unavailable abstract where sources cannot support the ideal minimum. For later reports and media, attempt the same extraction but allow a useful reviewed record with work, survey, cycle precision, and theme alone. Variables and abstracts remain nullable. Show missing-field counts so coverage is visible.

## Source strategy

1. **Seed from curated research bibliographies.** The [Canadian Research Data Centre Network (CRDCN)](https://crdcn.ca/) says its bibliography contains over 5,000 publications; its [public catalogue](https://crdcn.ca/publications/) and work pages can provide title, authors, year, DOI, abstract, and a “Data Used” section. The section can also be empty, as on [this CHMS article](https://crdcn.ca/publication/examining-the-prevalence-of-hepatic-steatosis-and-advanced-fibrosis-using-non-invasive-measures-across-canada-a-national-estimate-using-the-canadian-health-measures-survey-chms-from-2009-2019/). [Statistics Canada points to that bibliography](https://www.statcan.gc.ca/en/microdata/data-centres/data) for RDC research outputs. Use these pages as discovery and provenance, subject to practical access and reuse review. Their dataset labels are candidate program links, **not exact cycle claims**: for example, a [2005 CCHS paper](https://crdcn.ca/publication/aggregate-level-community-characteristics-and-health/) is tagged to a broad “CCHS Nutrition 2004 to 2015” dataset entry. The paper's own methods or abstract must settle the cycle.
2. **Deduplicate and enrich by persistent identifier.** Use DOI when available, then canonical publication URL/source ID. [Crossref's REST API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/) can add title, date, authors, ORCID/ROR when deposited, work type, and source links. [OpenAlex works](https://help.openalex.org/data/works/attributes/) can help find accessible copies and abstracts. Merge preprint/journal versions only when a source establishes the relationship; keep version records when it matters.
3. **Look for usage evidence in the work.** Title and abstract are good discovery and topic inputs. Methods, data, sample, tables/appendices, and dataset citations are the primary evidence for survey/cycle use. A publisher page, open full text, public PDF, or user-provided copy may supply these sections. Record access status, source URL, document hash, section/page, and extraction date. Do not claim cycle precision from publication year or a bibliography's dataset coverage range.

### Acquisition interfaces and limits (verified 2026-09-30)

Use a provider's documented API for machine retrieval when available; page extraction is an adapter for catalogues without one, not an API requirement. Keep each adapter's retrieval and reuse rules separate.

| Source | Machine access and pipeline role | Limit to preserve |
| --- | --- | --- |
| **CRDCN** | The [publications catalogue](https://crdcn.ca/publications/) is the curated seed and the source of `found_in_crdcn`. Work pages can include DOI, abstract, survey evidence, and RDC metadata. No **documented public bibliography API** was found in the CRDCN site reviewed for this plan. Ask CRDCN about an export/API before a bulk harvest; for a small pilot, test permitted catalogue-page extraction and incremental rechecks. | CRDCN membership is not proof of an exact survey cycle. Empty “Data Used” fields and imperfect text occur; preserve original page URL and field provenance. Check access rules and robots before automated page fetching. Do not build on an undocumented site endpoint as a stable contract. |
| **OpenAlex Works API** | [Documented REST API](https://help.openalex.org/api/) for discovery outside CRDCN and DOI/OpenAlex-ID enrichment. [Works search](https://help.openalex.org/api/searching/) covers titles, abstracts, and indexed full text; [DOI filters](https://help.openalex.org/api/filtering/) and `select` support targeted lookups. Use its [OA location fields](https://help.openalex.org/data/works/attributes/) to find accessible methods text. | A free key has a daily usage budget; monitor returned cost/remaining headers and back off on 429. Batch up to 100 DOI IDs in one OR filter, request only needed top-level fields, and use cursor paging for large searches. **`from_updated_date`/`from_created_date` sync filters require a paid plan**, so the free pilot must not depend on them. Search hits are candidates, not verified use. Abstracts are inverted indexes and require a separate republication-rights decision. |
| **Crossref REST API** | [Public API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/access-and-authentication/) for DOI/title/author/date enrichment and incremental DOI metadata refresh. Use the polite pool with a contact email, `select` fields, and bounded [created/update/index date windows with cursors](https://www.crossref.org/documentation/retrieve-metadata/rest-api/tips-for-using-the-crossref-rest-api/). | DOI metadata rarely establishes which dataset was analyzed. Cache responses; keep the same filters on every cursor request, reconcile duplicates, honor returned limits/429, and do not assume deposited abstracts can be republished. |
| **Unpaywall (optional)** | Its [DOI API](https://unpaywall.org/api/v2) can provide a second open-access location when OpenAlex has no usable copy. | Requires an email and has a published daily call limit; a location is a lead, not permission to store or redistribute the PDF. Call only for works still missing methods evidence. |

Do **not** attempt to traverse all OpenAlex or Crossref works for this use case. Use a versioned list of Statistics Canada survey names/acronyms and known work IDs to form bounded searches, then evaluate false positives on the gold set. Because an API index may miss analyses whose survey name appears only in the PDF, add targeted bibliography/repository discovery later. For OpenAlex Free, persist searched query/year windows and revisit a rolling recent-publication window plus sampled older windows; use a paid sync filter or licensed change feed only if measured freshness justifies it. CRDCN catalogue change detection is separate from Crossref/OpenAlex metadata refresh.

**Coverage stages:** (1) CRDCN and academic works outside CRDCN, using bibliographies, publisher records, DOI indexes, and open repositories; (2) Canadian federal, provincial, and municipal reports; (3) Canadian NGOs and think tanks; (4) international government and organization uses; (5) media mentions, lowest priority. Keep `found_in_crdcn` and all other discovery sources on the work, alongside publisher/issuing organization and sector. A work can be in CRDCN *and* another index; source membership is not an exclusive classification. For later non-academic works, distinguish a documented analysis of StatCan data from a quotation, citation, or passing mention; only the former enters usage counts.

Abstract availability and republication rights differ. [Crossref says some deposited abstracts remain under publisher/author copyright](https://www.crossref.org/documentation/retrieve-metadata/), and [OpenAlex does not ship plaintext abstracts for legal reasons](https://help.openalex.org/data/works/attributes/). Store an abstract's source, language, rights status, and text when reuse is permitted; otherwise keep the link and a short original topic description for public display. Do not assume that an API returning text grants republication rights. Full article text is a temporary/local extraction input where access permits, not a default public database field.

## Identity and evidence model

| Entity | Required idea |
| --- | --- |
| `research_work` | Stable work ID (DOI or source ID), title, type/sector, date, issuing organization/publisher, publication URL, abstract text when permitted plus provenance/rights/language, dedupe/version status. |
| `research_work_source` | One row per discovery/catalogue membership (`CRDCN`, Statistics Canada, Crossref, OpenAlex, publisher, government, NGO, etc.), source URL/ID and retrieval date. Derive `found_in_crdcn` from membership; do not treat DOI enrichment as proof that a work is outside CRDCN. |
| `research_work_author` | Work-local ordered authors; ORCID and institution IDs only when the source supplies them. Never infer a stable person ID from a name string. |
| `research_dataset` | Canonical survey program identity, optional cycle/reference period and file type, plus aliases and links to one or more Searcher `survey_group` values. A corpus group can contain multiple cycles. |
| `research_data_use` | Work → program/cycle claim, with role (`analyzed`, `comparison`, `background_mention`), precision (`exact_cycles`, `range`, `program_only`), source section/page and internally retained evidence span, extraction method/model version, review status. Store several exact cycles as several relations; keep a vague range as a range. Public display can use a source link and short excerpt only where reuse permits. |
| `research_link_assertion` | Separately retain externally supplied literature–data links: source provider, assertion and retrieval dates, work/dataset identifiers, direction, original relation type, and assertion provenance. Map compatible links to [DataCite relation types](https://support.datacite.org/docs/connecting-to-works) such as `IsCitedBy` or `IsReferencedBy` from the dataset's perspective, preserving the source wording. This is a discovery and interoperability record, not proof of `analyzed` use or an exact cycle. |
| `research_theme` | Versioned paper-level theme vocabulary; one reviewed primary and optional additional themes per work, with source (`author_keywords`, provider, or Hermes suggestion), rationale, and review status. A survey's subject classification is not the work's research theme. |
| `research_variable_mention` | Optional verbatim name/code/construct with source location and a candidate or reviewed `corpus_variable.record_id` link. A link requires same survey/cycle and supporting evidence; never inherit it from `research_data_use`. |

Only reviewed `analyzed` claims appear in use counts. A work that merely cites the survey as background remains searchable but does not increment those counts. [Scholix](https://www.rd-alliance.org/group_output/scholix-metadata-schema-for-exchange-of-scholarly-communication-links/) provides an exchange model for literature–data links; [DataCite's citation/reference relation types](https://support.datacite.org/docs/contributing-citations-and-references) describe link direction and kind. Preserve these external assertions as evidence leads and keep them distinct from our evidence-based use classification. `IsCitedBy` means the related work cites the dataset; `IsReferencedBy` means it references the dataset. Neither means the work analyzed it. A program-only claim can appear under a survey's publications with “cycle not stated”; it must not be distributed among cycle bars. Where a paper says “ten CCHS cycles from 2000 to 2014” without listing the ten, record a range and unknown exact members rather than expanding every intervening cycle. One paper may have several `analyzed` claims for linked datasets or pooled waves.

Keep the full candidate/rejection history locally. Publish source-attributed, reviewed facts and clearly marked machine-extracted facts only after a measured quality gate. Publication links must not be represented as official Statistics Canada usage statistics or as endorsements by authors, publishers, CRDCN, or Statistics Canada.

## Hermes pipeline: bounded, resumable batches

```text
source discovery → identity/DOI normalization → abstract and methods acquisition
→ bounded evidence chunks → Hermes extraction (survey, cycle, themes, variables)
→ deterministic checks + reviewer → survey/cycle resolution
→ approved export → Researcher index and metrics
```

Build `tools/research/researcher` as the reusable Node-side package/CLI. It owns source adapters, normalization, a local `node:sqlite` WAL queue, reviewer rules, exports, and tests. Reuse the *pattern* in `tools/metadata/statcan-corpus/src/graph/queue.ts`—atomic leases, stable job IDs, capped retries, status reporting, idempotent export—without coupling publication jobs to the derivation queue or its variable schema. The Hub can host the first Researcher UI while the package remains separable under `ARCHITECTURE.md`.

Queue **one work and one task stage at a time**, not whole bibliographies in an LLM prompt. Extract the methods/data section deterministically where possible; give Hermes a bounded passage plus title/abstract context and a small candidate survey alias list. Process long methods sections in overlapping chunks, then reconcile claims for that one work. Run a single local inference worker or a measured small concurrency limit for VRAM stability. Job IDs include source hash, stage, prompt version, and model version so a changed paper or parser creates a new reviewable result. Structured output requires survey-name text, cycle text, use-versus-mention role, exact evidence quote/location, proposed primary/additional themes with a rationale, and optional variable mentions; “unknown” is a valid answer. Abstract acquisition/rights checks and source membership are separate deterministic stages.

### Work-saving controls

1. **Discover narrowly, then enrich by ID.** Start with CRDCN work URLs and bounded OpenAlex survey-name/acronym queries. Normalize DOI case/URL forms, CRDCN URLs, and OpenAlex IDs before fetching Crossref/OpenAlex details. Store all source memberships for one work; match title/author/year only as a reviewable fallback. Keep preprint and final-publication identity decisions explicit.
2. **Checkpoint each source adapter.** Persist provider query, cursor or page, retrieval time, response status, provider ID, response/content hash, and parse version in the local queue. Use bounded date windows where supported. Re-run extraction only when the source content or extractor version changes; use conditional requests where the provider supports them. Apply per-host pacing, retry with backoff and jitter, and quarantine repeatedly failing records without stopping a batch. Never put provider API keys in the browser or GitHub Pages bundle.
3. **Gate costly text acquisition.** A deterministic first pass on title, abstract, CRDCN labels, and survey aliases creates a candidate list. Fetch a permitted methods/full-text copy only when survey/cycle evidence is missing or ambiguous. Prefer structured article sections over whole-PDF OCR; keep section/page offsets and a text hash. Store no full PDFs or large extracted text in D1.
4. **Reserve Hermes for decisions.** Resolve unambiguous DOI identity, survey aliases, explicitly named waves/cycles, and simple keyword evidence with deterministic code. Send Hermes only short relevant passages plus canonical survey/cycle candidates; ask it to abstain on unsupported claims. Validate every returned evidence quote against the exact input passage. Route conflicting survey tags, vague periods, possible background mentions, and construct-versus-variable ambiguity to human review.
5. **Measure yield and quality by stage.** Track candidates found per source, overlap, DOI/abstract/methods availability, reviewed analyzed claims, exact-cycle rate, false-positive rate, review minutes, LLM calls/tokens, and retry/429 rates. Compare CRDCN-only, API-only, and union recall on the gold set before expanding source searches. Publish source coverage and missingness with usage metrics; do not interpret indexing growth as growth in actual data use.

The reviewer checks that the cited span exists in the input, the survey alias resolves to a known program, the cycle is explicitly supported, and the work is about actual analysis rather than a plan, literature review, or cited predecessor. Contradictions between abstract, methods, and CRDCN tags become `needs_review`. Keep source wording and the normalized interpretation side by side. Reuse the existing human accept/reject idea, but define publication-specific statuses and commands.

## Hosting decision for Researcher

Researcher is a new data product, so its persistence need not consume the current Searcher database. The [2026-09-30 audit](searcher-vector-audit.md) measured the live Supabase project at 311 MiB against its [500 MB Free database limit](https://supabase.com/docs/guides/platform/database-size). **Use a durable database as the source of truth for reviewed works, abstracts where reuse permits, and survey/cycle links.** Local `node:sqlite` is only Hermes's resumable job queue and staging area; losing that file must not lose the published catalogue. Keep full article PDFs outside the relational catalogue, subject to access and reuse rights.

A publication database is unlikely to be too large just because it holds abstracts. As an order-of-magnitude illustration, 5,000 abstracts averaging 2 KB are about 10 MB of raw text; titles, authors, links, evidence, and search indexes add overhead that must be measured. This is an illustration, not a size estimate for the complete catalogue. Measure actual database and index bytes at pilot scale.

**Revised recommendation:** pilot **D1 + Worker** for reviewed Researcher records, with local SQLite only for Hermes's queue and unpublished candidates. Keep the GitHub Pages Hub, and join to Searcher's Supabase graph through stable program/cycle/variable IDs at the application layer. Compare a separate Supabase Free project before provisioning if a slot is available; choose Supabase Pro on the existing project if a single database and lower integration effort justify $25/month. Keep Oracle off the near-term path. Do not migrate `corpus_variable` or Searcher lineage to D1. The final host follows measured storage, indexed query cost, restore/export, and API latency in the pilot.

### Boundary with the rest of Modular Survey Tools

The D1 recommendation applies **only to the new Researcher catalogue**. Searcher already depends on PostgreSQL `tsvector`/GIN search, trigram matching, multiple graph/search RPCs, RLS, and Supabase Storage for source documents. D1 could represent its records and links, and supports FTS5, but moving Searcher would require rewriting its SQL/search behavior, API adapter, access policies, and document delivery, then rechecking relevance and every graph count. D1 Free's 500 MB *per database* limit also gives no assured capacity gain over Supabase Free until a representative SQLite import is measured. Keep Searcher in Supabase under the [existing audit decision](searcher-vector-audit.md).

Collector, Respondent, Validator, Analyzer, and CATI use the production Supabase tables for survey definitions, sessions, responses, paradata, cases, rules, and corrections; photo attachments use Supabase Storage. A D1 replacement would need a Worker API for those writes and reads, new authorization in that API, an object-storage path for attachments, and migration of existing data and clients. D1's [single-database query serialization](https://developers.cloudflare.com/d1/platform/limits/) is another workload to test for concurrent respondents. This is technically possible but not a storage-only switch. The current Supabase demo policies are public by design; real or sensitive collection would require the planned access-control hardening regardless of provider.

Revisit whole-suite hosting only if measured cost or capacity justifies that rewrite. The nearest low-effort capacity options are a second Supabase project for the corpus, where the existing `VITE_CORPUS_*` adapter seam already exists, or [Supabase Pro](https://supabase.com/pricing) for more space in the current project. Neither change is part of the Researcher D1 pilot.

## Product surfaces, outputs, and documented use

- **Searcher → Usage of Data:** selected survey/cycle, reviewed analyzed-work count, years/topics preview, unresolved-cycle count, and a link to Researcher with the filter carried in the URL. Show citation/reference links separately when available. Avoid variable-level claims here until a later evidence project verifies them.
- **Researcher:** browse/search outside public works by one or more selected surveys, cycle, theme, publication year, sector/work type, CRDCN inclusion, and author. Show title, permitted abstract or source link, method evidence citation, review/precision label, DOI, optional reviewed variable mentions, and related works using the same survey. A user responsible for several surveys can see one combined, deduplicated article list. The current Hub page is a three-work, reviewed static pilot with survey filters and source links; richer filters and durable storage remain follow-on work. A standalone app is a later deployment decision.
- **Outputs and use metrics:** distinct reviewed analyzed works per survey and cycle, publication-year time series, survey comparisons, primary/additional theme coverage, exact-cycle versus program-only proportion, CRDCN versus outside-CRDCN coverage, sector, and trend changes. Keep separately labeled counts of citation/reference link assertions; do not add those to analyzed-use counts. Multi-survey works count once in each relevant survey and once in an overall or multi-survey selected total; pooled exact cycles count once in each relevant cycle and once in their survey total. Program-only and vague-range works appear in an unresolved-cycle bucket, not in exact-cycle bars. Use publication year for trends, with `year unknown` separate; never silently substitute ingestion year. Label counts “observed publications in indexed sources” and “reviewed publications analyzing this dataset”; never call these outcomes, impact, a census of data use, or author productivity scores. Let the user inspect the works behind every count and see source coverage and missingness.
- **Collaboration:** start with shared-data/shared-topic discovery and public ORCID/publication links. Invite researchers to claim a profile or opt into contact only when a later feature needs interaction; do not auto-message them.

## Pilot and acceptance gates

1. **Source/rights audit:** choose two contrasting survey programs (CIUS and CCHS are good candidates), collect about 100 outside public works across CRDCN, other publishers, government agencies, and DOI indexes, including duplicates and background-only mentions. Record issuing organization, source availability, and abstract/display rights.
2. **Gold set:** manually label work identity, CRDCN membership, analyzed versus mentioned, program, exact cycle(s) or unknown/range, primary/additional themes, abstract availability/rights, optional named variables, and evidence location. Include papers that pool waves, use linked datasets, have a misleading bibliography tag, or appear in CRDCN and elsewhere. This becomes the evaluation set before tuning Hermes.
3. **Queue extraction:** run the one-work bounded pipeline, inspect hallucinated/unsupported spans, VRAM use, throughput, retry behavior, and cost of human review. Report precision and recall separately for program, exact-cycle, theme, and named-variable claims; require a high-precision verified tier before public counts.
4. **Storage and read spike:** build the same reviewed-work schema/query sample locally in SQLite and Postgres, then test D1 + Worker as the first hosted candidate. Measure database/index bytes, FTS5 and survey/year/theme query latency, D1 `rows_read`/`rows_written`, Worker CPU/requests, CORS, authenticated imports, exports/restore, and cross-store ID resolution. Compare the measured result with a separate Supabase Free project if available and the existing project's Pro upgrade; test Turso only if D1's free limits or operational fit fail. Do not provision a long-lived host before this gate.
5. **Public vertical slice:** replace the static Researcher pilot with reviewed records backed by the selected durable database and add Searcher's Usage of Data entry through a public read path with appropriate access controls and caching if needed. Verify all displayed links, abstracts/rights, CRDCN provenance, evidence, count semantics, multiple-survey selection, year trends, and empty/unknown states.
